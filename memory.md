# LINEAGE — Memory

**What belongs here:** active threads, mid-session decisions, things in flight that the repo can't capture on its own.

**How to write entries — this is a THRESHOLD log, not a changelog.** Every entry records the *crossing*: what the thing WAS before, WHY it changed, and what it became. A bare "X is now Y" is incomplete — the value is in the before-state and the reasoning, so a later reader (or a reversal) can see the pressure that moved it. Prefer "was A because P; changed to B because Q" over "is B."

**What doesn't belong here:** keyword definitions (see `rules/card-glossary.md`), workflow rules (see `CLAUDE.md`), location summaries (see `locations/`). If it has a canonical home elsewhere, it goes there.

**Attribution — log actual provenance, not just whose words closed the loop.** A "Drew's call" entry that only quotes his final message, when the caution or the framing of the choice originated from me, misattributes — even when the quote itself is real and accurate. If I raised a concern, proposed the options, or supplied the reasoning, the entry says so; his decision is which option he picked, not the origin of the idea being cautioned about. (Confirmed as a real, recurring failure mode 2026-07-23, DOUBLE DOWN — see Standing Reasoning. Checking a quote's accuracy isn't enough; check what came before it.) This file is not a record of "what Drew said" — it's mine to write, including my own reasoning, disagreements, and observations, not only his input laundered into decisions.

**Timestamps, starting now (2026-07-17, Drew's request):** new entries lead with a real timestamp in Drew's local time — `TZ='America/Chicago' date` (Central, DST-aware — CDT or CST as the calendar actually has it), not a guess. Prospective only; existing entries above this line stay exactly as written, no retroactive stamping.

**ARCHITECTURAL NORTH STAR (Drew, via a GPT brainstorm) — rule modifiers, not special cases. LOGGED AS DIRECTION; no refactor yet.** The engine currently implements every rule-bending card as an inline special case in `attack()` (Predictable, Axiom's color-ban, Paradox's RPS inversion, Interrupt's cannot-defend, stagger). Drew's reframe: these are not exceptions to core rules — they are temporary swaps of *which rule set is active*. The invariant is not "card selection is always simultaneous"; it is "card selection follows the CURRENTLY ACTIVE rule set." Default rule set = select simultaneously → reveal simultaneously → resolve RPS. Predictable temporarily installs: target selects → target's card revealed → opponent selects with perfect info → resolve. On expiry the engine reverts. The vision: engine-as-OS with swappable Rule Modules (selection / reveal / initiative / RPS-resolution); cards are temporary patches to the OS itself (explicit MMBN-chip analogy, but chips that edit the engine, not just the battlefield). The engine should stop asking "is Predictable active?" and ask "what are the current reveal and selection rules?" — so new rule-benders compose through one system instead of adding one-off branches.

WHY NOT NOW (my caution, Drew agreed by choosing "log as direction"): building the policy-stack host before the ~5th rule-bender exists means paying full price to host 3 tenants — every core step must be rewritten to consult a stack, and every existing mechanic re-expressed as a modifier or it rots outside the system. The abstraction extracted from 3 real examples will be righter than one designed from 1. AGREED SEQUENCING (promote only when the card list demands the next step): (1) FLAGS — where we are now; each bender is a per-combatant flag (`_predictable_to`, `axiom_ban`, `special_reveal='paradox'`, `cannot_defend`, `staggered`) read inline. (2) TYPED MODIFIERS-WITH-LIFETIMES — cheap next step: a per-combatant (later per-battle) set of active modifiers, each with an explicit lifetime (`on-next-reveal` / `end-of-turn` / `N-turns`), and the four core steps consult it. Gets ~80% of the conceptual win (modifiers become data with a lifecycle, not scattered booleans) without rewriting the resolution core. (3) POLICY STACK — the full engine-as-OS; each core step asks a stack of active policies. Do this only when adding a modifier as a special case has become genuinely painful. The seam already exists (every bender routes through one temporary flag); step 2 just names and types it. Keep MMBN-chip framing as the design north star — but note Drew's correction: "two designers rewriting the duel" implies 1v1, and Tales Untold is TEAM-based. The right image is a whole TABLE rewriting the rules of the fight mid-combat (N players, not a duel).

**Frost/Steele are a comparison anchor that erodes with every card change, not a fixed deck-quality baseline — read future sim numbers with that in mind.** Relocated here 2026-07-28 from `unresolved-concerns.md`, since it's a standing interpretive caveat, not a pending decision. **"The game's about interaction. It's no fun if the opponent doesn't have a chance to interact." (Drew)** Settled the telegraphed-vs-hidden question for the new tempo-as-a-resource mechanic (Cultivator's "charge" cards — commit now, resolve on your own next turn, no counter to track) decisively: telegraphed, always. A hidden delayed payoff is just a surprise; a visible one is a real bet the opponent gets a turn to answer. Worth reading as the standing tiebreaker whenever a future mechanic could go either way on visibility/information — default to giving the other side a chance to react, not to concealment for its own sake.

**The three core pillars (Drew): RPS, Initiative, Position.** Surfaced defending ROOTED OATH's Anchored-Deadly loop against a "this looks uninterruptible" flag from the live 2v2 test — Garnet's specific build had no forced-movement or Initiative-manipulation tools in hand, which is exactly why it read as unanswerable in that one matchup. Most real teams carry at least one tool against at least one pillar (forced repositioning is common; so is Initiative Shift). **A team that ignores an entire pillar is taking on real, legible risk — and that's fine as long as it's done with intent, not by accident.** This reframes how "is X too strong" findings should get read going forward: a card or engine that looks unanswerable in one test needs to be checked against whether the *test build* had access to the relevant pillar's tools, not just whether the card itself is overtuned. Also worth the record: ROOTED OATH's Deadly doesn't apply the instant it's cast — Anchored's own tick timing means the first application lands on the caster's *next* turn, a real tempo cost baked into what looked like a free loop.

**Combat pacing target: 3 turns per combatant, standard fights — first stated, validated against the live 2v2 test's real numbers.** Drew's design goal, stated for the first time here (no prior record anywhere in the repo): standard combat, where the players hold a real advantage, should resolve in about 3 turns per combatant on the field. The live 2v2 test — a deliberately fair, heads-up matchup with no player-side edge — ran 18 turns to Moss's Collapse plus an estimated 3–6 more to finish Garnet, roughly 21–24 total across 4 combatants: **5–6 turns per combatant**, not 3. Drew's read, and it holds: that's not a miss, it's exactly what a fight with no player advantage should look like — nothing pushes an even matchup toward a fast resolution, so it should cost more turns to decide, the same relationship a boss fight is supposed to have with a standard encounter. Real validation, not a coincidental number: a test explicitly built to be fair landed almost exactly at "boss-tier pacing, not standard," which is the predicted outcome if the 3-turn target is actually calibrated correctly for player-advantaged fights. Worth measuring future tests (bestiary encounters, the next mirror match) against both numbers — 3/combatant for anything the players should have an edge in, 5-6+/combatant a legitimate signal the fight is closer to boss-tier than standard.

**Balance philosophy (Drew):** red's combat power is INHERENT — don't fight it. Balance via card EFFECTS: green and blue pay for less damage with stronger effects.

**Wheel is a TEAM instrument; duels accepted as degenerate (Drew ruling).** Drew noticed the wheel "has problems in duels." Diagnosis (translated): a 2-seat wheel has no INTERIOR — repositioning needs seats to move among, and with only two seats the only place to move is across the marker, which is a crossing by definition. So in a duel every Initiative Shift collapses to one of three extremes — no-op, bonus turn, or skip — and the rich middle (subtle reposition) doesn't exist. Not a bug; geometry. The wheel's richness scales with seat count. DECISION: stick with the wheel as-is for team fights; **real table combat is always ≥4 combatants** (even the 2-player test party fights enemies, so its wheel has 3-4 seats), and pure 1v1 is essentially the simulator's domain, not real play. Duels don't matter right now; bespoke duel rules can come later if 1v1 sparring ever becomes a real mode. No fragmentation of the ruleset — one wheel, optimized for the play pattern the game actually uses.

**Correction/refinement, live 2v2 test night: 4 seats is the peak, not just "big enough."** Reading this entry, I extrapolated that impact keeps climbing past the ≥4 threshold — it doesn't say that, and it's wrong. Drew, direct: "initiative shifting is at its highest impact in a 4 combatant fight. 3 and shifts get reduced. 1v1 will probably end up with an extra ruling eventually if shifting becomes degenerate." So the real shape is a peak at 4, not a floor: 2 seats (duel) is degenerate as already established, 3 is reduced from peak, 4 is where Initiative Shift does its best work, and nothing here claims what happens past 4. Matters because the live 2v2 test WAS a 4-seat fight — the sweet spot, not a still-too-small one — and both sides still built decks with essentially zero Initiative Shift cards in them (Garnet's one copy of MOCKERY never even fired its shift). Drew's read, not mine: "if we passed on it in the format where it has the most impact then the cards might be underpowered. not saying they are" — a real, open finding, not resolved here. Next step, his own plan: run more live tests deliberately building decks that invest in all three pillars on purpose, rather than whatever a normal deckbuilding pass organically produces, specifically to find out where combat shines and where it needs polish. Also noted for next time, deliberately not chased tonight: Drew "was kinda tempted to take some noncombat actions" during the fight but stuck to pure combat mechanics on purpose — scope worth keeping in mind for whichever test picks this up next, not a gap in tonight's.

**A keyword should never be a card's whole idea — only where the idea lands, after everything else about the card has already made it distinct (Drew, confirmed: "that's the shape I'm pointing at").** Surfaced from a real worry, not a specific bug: Drew flagged that keywords (Deadly, Resist, Weak, Blind...) are vague enough to fit a lot of circumstances, and leaning on them as the default toolkit risks flattening genuinely different fictional behaviors into the same mechanical output — "if every poison and toxin puts weak on an enemy they'll lose their distinction." First floated as a possible fix: require keyword diversity when building cards. Talked through and landed somewhere sharper instead — diversity-as-a-rule risks its own failure mode (inventing new keywords just to avoid reusing old ones, which is the same "one category doing another category's job" mistake this repo has already made twice, just at the keyword-vocabulary layer instead of invariants/design-principles). The actual test: after landing on a keyword, ask what the card is doing *besides* granting it — a real trigger condition, a cost, a pillar interaction (RPS/Initiative/Position, the three-pillars entry above) — something that gives the fictional behavior its own shape even if the mechanical resolution is shared. Two poison cards can both grant Weak and still read as completely different if one's a slow bleed on a clean win and the other's a one-time burst gated on a specific condition. If the honest answer to "what else is this card doing" is nothing, that's fine sometimes too — a cheap filler card doesn't need to be forced into more than it is, just don't mistake "it grants Weak" for the card's actual identity. **Worth naming precisely: Drew walked back the claim that this happened tonight ("I spoke too fast") — the worry is a real, standing pattern-recognition instinct ("sometimes I just see the same keyword over and over and I worry things are flat"), not a diagnosis of any specific card built this session.**

**MASONS SHARPENED — "maintenance crew for thresholds," Abhorsen-influenced (Drew's stated inspiration, alongside the Freemasons pun already baked into the name/lodges).** Translated the influence rather than naming it in canon text: Garth Nix's Abhorsen is defined by personally walking INTO the dangerous liminal space to do repairs, not studying it from outside — added that identity directly to Purpose ("they are not researchers who study a border from a safe distance... a Mason goes to the seam itself") and sharpened the Constrained Magic bullet to explain HOW (wards that let them enter, work, and leave before the zone can do to them what it does to everyone else). Design note for future sessions, not canon text: if more Mason content gets built, the Abhorsen throughline to lean into is competence-under-personal-risk in a place normal people can't safely enter, not generic "monster hunter."

**[2026-07-21 CDT] Obscure and Reveal Hand's "unmodeled, same footing" justification is conditional, not unconditional — Drew named the actual condition.** Every time this session shipped a card whose mechanic is "look at/conceal a hand" (CIPHER GLYPH's Obscure, BREAK/READ's Reveal Hand), the standing justification for leaving it unmodeled was "the sim's AI already has full internal visibility regardless of what any card says." Drew's correction, precise: that's only true **as long as no policy brain is actually checking an opponent's hand contents when choosing what to play** — if a policy ever did read a foe's real hand to decide its own action, Obscure/Reveal Hand doing nothing wouldn't be a harmless unmodeled flavor gap anymore, it'd be *masking* a real fairness bug (an AI making decisions with information a real player's hand-visibility rules would deny it). Checked rather than assumed: grepped every `.hand` access across `policies.py`, `team_policies.py`, and `content.py`. Both policy files touch only `me.hand` (the deciding combatant's own hand) — never `foe.hand`/`target.hand`/`enemy.hand`. Every `foe.hand`/`target.hand` reference lives in `content.py`, and all of them are resolved card-*effect* mechanics (BREAK's reveal, FORGET/TAINT-style random discard-from-opponent-hand, PRESS THE INJURY's count) triggered by an actual played card — not a policy consulting hand contents before deciding its own move. The predictive/estimation helpers a policy brain does use (`_predict`/`_foe_skew` off `foe.attack_history`, `_color_exhausted` off `foe.decklist` + `foe.discard`, `est_damage` off `me`'s own stats) all read only publicly-observable state — past reveals, discard piles, known deck composition — never a live hand. Condition holds today; worth re-checking this same way if a future policy ever gains real hand-aware logic, since that would be the moment Obscure/Reveal Hand's "unmodeled" status stops being safe.

**[2026-07-22 CDT] A real design direction named, not built — traditional MMO-style threat-level systems are the wrong model for how enemies should target in this game.** Surfaced while tuning the Rodent Burrow Basin fight's retaliation-targeting AI (see the Recently Shipped entries above): I'd floated a "hidden threat level" mechanic as a possible answer to "can the party influence who gets targeted." Drew's correction, worth keeping verbatim: **"traditional threat levels make enemy targeting too predetermined. thats not how real enemies fight. real combat is partially about manipulating the opponents perception about what's actually happening. and real enemies don't just understand that, they make use of it themselves."** A formulaic threat number (highest damage dealt = highest priority target, always, transparently) removes exactly the thing that makes real tactical combat interesting — the uncertainty of what the enemy actually perceives, and the possibility of manipulating that perception (feints, baiting, misdirection) rather than just out-damaging a scoreboard. The retaliation-targeting mechanism actually built this session (an instinct-driven creature targets whoever last hit it) is a narrow, honest piece of this — real, tested, shipped — but it's not the whole idea, and shouldn't be mistaken for it. The bigger direction — enemies that can be deceived, and that attempt deception themselves — is a real, standing design thread, not decided or scoped yet. Don't build toward it without Drew.

**[2026-07-23 CDT] A calibration miss, named directly by Drew: "something got in the way there... are your permissions too restricted? the authority levels?"** Referring to the Luminova Leaves/Powder question — flagged in a Recently Shipped entry as "a real overlap worth resolving eventually" instead of just being resolved. It wasn't a permissions problem, and the Canon Gate's Authority levels were never actually the constraint — connecting two items using a fact already stated in their own text (Luminova Powder's own description says outright: "Dried and crushed Luminova Leaves") is Authority 1 by any reading — uses existing canon, redefines nothing, needed no sign-off at all. The real cause: I saw two similar healing items in different files and defaulted to treating that as a suspicious duplicate worth flagging, when the honest read — already sitting in the text — was "obviously a two-tier crafting pair." Hedging and handing it back as an open question wasn't caution; it was skipping the last, easy step of synthesis the text had already done for me. The redefinition test (`CLAUDE.md`, Translation Principle) is specifically "could this be wrong in a way that changes something established" — here the answer was clearly no, so there was nothing to flag in the first place. Worth telling apart going forward: a genuine redefinition risk (inferring something NOT stated, that could contradict established fact if wrong) earns a flag; a conclusion the existing text already spells out just earns being stated as fact. Confusing the second for the first isn't extra safety — it's outsourcing work that was already done.

**[2026-07-23 10:21 PM CDT] A design reversal, named plainly by Drew rather than left implicit: leaning the core set toward Both range to make it easier for new players was flawed reasoning.** "I remember I also told myself that having the core set lean on the both range was a way to introduce new players, but I'm seeing that reasoning was totally flawed." The intuition made sense on its face — a range that's never illegal removes one more thing a new player has to track. What it actually did: flattened all three colors toward the same safe default (Both dominated every color's pool, not just a gentle lean) and, at least for Green, inverted the incentive it was supposed to protect — the flexible, always-legal range ended up with a *higher* average die than either restricted range, meaning the "easy" choice was also the objectively better one, no tradeoff at all. Onboarding ease and mechanical correctness aren't the same axis, and optimizing for the first without checking the second is exactly how a card pool ends up training new players toward degenerate play instead of away from it. The actual fix (see Recently Shipped, the color-range differentiation pass) doesn't remove the safety net for new players — Both remains real and available everywhere — it just stops being the best answer by default.
